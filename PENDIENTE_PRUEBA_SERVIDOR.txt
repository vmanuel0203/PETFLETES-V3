PetFletes - adaptación a Postgres: PENDIENTE DE PRUEBA EN SERVIDOR
===================================================================
Estado: el código está escrito pero NUNCA se ha ejecutado contra un servidor Postgres real.
Lo único comprobado hasta ahora (python test_v2.py, sin servidor):
  - SQLite funciona igual que antes (pruebas 1 a 3).
  - Las piezas de adaptación funcionan con objetos simulados (prueba 4): traducción de ? a %s,
    filas por nombre/índice, Decimal->float, lastrowid vía RETURNING, conversión del esquema, candado.
Todo lo demás debe verificarse en un proyecto de PRUEBAS. Cada sitio adaptado está marcado en db.py
con "PG-PENDIENTE-PRUEBA" (búscalo con Ctrl+F).

COMO PROBAR (Windows, proyecto de pruebas de Supabase; NUNCA con datos reales)
  1) pip install -r requirements.txt
  2) Pruebas automáticas contra el servidor (BORRA las 9 tablas de PetFletes de ese proyecto):
        set PETFLETES_TEST_DATABASE_URL=postgresql://...
        set PETFLETES_TEST_BORRAR_TABLAS=1
        python test_v2.py
     (la prueba 1 se omite en este modo: migra un archivo SQLite v1)
     Antes de pasar a producción: las 5 pruebas deben dar OK (la 1 aparece omitida) y la lista de abajo completa.
  3) La app contra el servidor:
        set DATABASE_URL=postgresql://...
        set PETFLETES_PG_PRUEBA=1
        iniciar.bat demo
  4) Solo cuando 2 y 3 pasen: poner PG_LISTO = True en db.py.

RIESGOS CONOCIDOS (sitios con más probabilidad de fallar)
  - actualizar_tienda: COALESCE(?, sinpe) con parámetro sin tipo (puede requerir CAST explícito).
  - Consultas con GROUP BY u.id que seleccionan otras columnas: válidas solo porque u.id es clave primaria.
  - Funciones que abren una conexión mientras otra sigue abierta: en SQLite fallaba con "database is locked";
    en Postgres puede esperar por bloqueos (pool de 5 conexiones).
  - Código que captura un error de base de datos dentro del mismo "with conexion()" y sigue usándola:
    en Postgres la transacción queda abortada (en SQLite no). Hoy los dos casos conocidos capturan fuera del with.
  - Postgres sí exige las llaves foráneas; un mascotas.db de la v1 (tablas sin REFERENCES) puede traer filas
    huérfanas que fallarían al copiarse. Lo manejará el script de migración (aún no escrito).
  - Si se copian datos con ids existentes, hay que reiniciar los contadores (setval) o los nuevos INSERT chocarán.
